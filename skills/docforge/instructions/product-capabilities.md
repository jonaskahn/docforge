# Product-capability writing craft

Group capabilities by user outcome rather than module or team boundary. Give each
capability a short, verb-first, outcome-named title — Jobs-to-be-Done phrasing for what the
user can now do, not what was built ("Export filtered results," not "Export module"). State
the audience it serves and one concrete outcome per capability; a capability that needs two
outcomes to describe is two capabilities.

Keep the inventory parallel and scannable: same fields, same order, every entry, so a reader
compares rows without re-learning the shape each time. Link to flows for behavior depth and
to reference documents for configuration or limits — this page names what exists and why it
matters, not how it works.

No current catalog entry generates this document type; the closest live neighbor is
`feature-catalog`, which reframes capability entries around value and status and points back
to a `capabilities.md` this instruction targets but that nothing currently produces. Treat
that as a known gap, not a cue to duplicate `feature-catalog`'s framing here.
