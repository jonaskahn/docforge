# Dependencies Inventory Instruction Template

## Purpose
Document external libraries, services, and their integration points.

## Target Audience
Engineers, ops (understanding what system depends on)

## Required Sections
1. Direct dependencies - external libraries and their purpose
2. Version constraints - what versions are pinned/required
3. Failure modes and fallbacks - what breaks if dependency fails
4. License compliance - license type per dependency

## Data Requirements
- Knowledge graph (for import/use patterns)
- Direct inspection (manifests: package.json, pyproject.toml, go.mod, etc.)
- Dependency registry lookups (if needed for license/status)

## Depth Level
L2 - What it is, why used, how it fails

## Template Structure
- Organize by category (build tools, runtime libraries, services, etc.)
- For each dependency:
  - Name and purpose
  - Current version and constraints
  - Where it's used (modules/packages)
  - Failure mode: what breaks if this dependency fails
  - Fallback/mitigation: can it be swapped out, can it degrade
  - License type and compliance implications

## Provenance Requirements
- Reference package manifest files for versions
- Tag uses with modules that import each dependency (from knowledge graph)
- Record version source (package lock file, git blob hash)
- Link to dependency registry entries if available

## Common Pitfalls
- Don't list transitive dependencies unless they're critical
- Don't duplicate version info - link to lock files instead
- Don't assume readers know what each library does - brief description per item
- Don't forget license compliance - critical for open source
- Don't ignore new/unpopular dependencies - especially important to document

## Notes
- Keep focus on what you depend on and why, not implementation details
- Include external services (cloud APIs, databases) not just libraries
- For critical dependencies, document the fallback story
- For security-sensitive dependencies, reference security.txt/SECURITY.md
