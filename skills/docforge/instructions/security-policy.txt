# Security Policy Instruction Template

## Purpose
Provide security contact info, vulnerability reporting procedures, and scope.

## Target Audience
Security researchers, incident reporters

## Required Sections
1. Reporting contact - how to report vulnerabilities safely
2. Scope and exclusions - what's in/out of scope for security reports
3. Response timeline - how quickly we'll acknowledge and respond
4. Recognition policy - how we credit reporters (if applicable)

## Data Requirements
- No data requirements (these are policy choices by repo owner)
- External values: <SECURITY_CONTACT>, <RESPONSE_TIME_HOURS>, <RESPONSIBLE_DISCLOSURE_URL>

## Depth Level
L1 - Clear, concise policy statement

## Template Structure
- Lead with: "We take security seriously. Here's how to report vulnerabilities."
- Reporting method:
  - Email address or security.txt contact (RFC 9116)
  - Do NOT use public issue tracker for vulnerabilities
  - Optionally: GPG key for encrypted submissions
- Scope: what types of issues are in-scope
  - Examples: authentication flaws, data exposure, injection attacks
  - Examples out-of-scope: non-exploitable implementation bugs, social engineering
- Response timeline:
  - Acknowledgment time (usually 24-48 hours)
  - Patch target (e.g., "within 30 days")
  - Disclosure timeline (when you'll go public)
- Recognition:
  - "We credit reporters in release notes" OR "We keep reports confidential"
  - Hall of fame or honor roll (if maintained)
  - Compensation policy (if applicable)

## Provenance Requirements
- Reference organization security policies if applicable
- Link to SECURITY.md RFC 9116 definition
- Cross-reference relevant architecture/limitations.md if known vulnerabilities exist

## Common Pitfalls
- Don't create this doc if you're not prepared to respond - inaction erodes trust
- Don't use overly restrictive scope - try to be helpful
- Don't forget email or contact method - it's the critical thing
- Don't make timelines unrealistic - undercommit and overdeliver
- Don't expose internal security process - keep it simple and actionable

## Notes
- This is usually a short document (under 1 page)
- Make contact method obvious - security reports are time-sensitive
- If you host on GitHub, you can use GitHub's security advisory feature
- RFC 9116 (security.txt) can be auto-discovered at /.well-known/security.txt
