# Architecture Low-Level Instruction Template

## Purpose
Explain how major subsystems work internally - detailed mechanism and data flow.

## Target Audience
Engineers implementing features or debugging issues

## Required Sections
1. Internal structure per subsystem - components, abstractions, layers
2. Call and data flow pathways - how data moves and transforms
3. Key abstractions and patterns - major design patterns used
4. Integration points - how this subsystem connects to others

## Data Requirements
- Knowledge graph (required - module map, layers, import edges)
- `/understand-explain <path>` for each significant subsystem (required)

## Depth Level
L3 - Implementation detail, readable without reading source

## Template Structure
Per major subsystem:
- One-line purpose
- Conceptual overview (1-2 sentences on the big idea)
- Main components and their responsibilities
- Call flow for common operations (happy path + key branches)
- Data structures and transformations
- Error handling and edge cases
- Integration with rest of system

## Provenance Requirements
- Tag each component with module path from knowledge graph
- Reference specific functions/types by name (but not line numbers - they change)
- Record git blob hashes of key modules implementing subsystem
- Cross-reference architecture/high-level.md for block-level context
- Reference flows/ for runtime choreography

## Common Pitfalls
- Don't paste code - describe what it does at behavior level
- Don't link line numbers - refactors will break links
- Don't go so deep you're explaining every helper function
- Don't duplicate high-level.md - assume reader read it first
- Don't assume readers know all the libraries/frameworks used - explain them

## Notes
- Aim for detail level where someone could implement a feature without reading source
- Use diagrams for complex flows (sequence, state, call-tree style)
- Explain why design was chosen this way (not just what it is)
- Link to `/understand-explain` output as reference for your assertions
